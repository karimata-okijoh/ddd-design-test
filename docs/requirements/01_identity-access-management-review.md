## 🔴 Critical（設計に着手する前に要確認）

### C-1. マルチテナント分離方式が未決定なのに実装設計が先行している

現在の設計は「シングルDB・`TenantId` カラムで行分離」を前提としているが、未決定事項では「スキーマ分離を推奨」と矛盾している。スキーマ分離に変更すると、`AppDbContext`・リポジトリのフィルタリング・インデックス設計がすべて変わる。**分離方式を先に確定**させるべき。

**関連箇所**: 519行（未決定事項）

### C-2. SystemAdmin 認証方式が未決定のままセキュリティ設計が進んでいる

テナント停止・削除などの最重要操作の実行者が、ロールで制御されるのかAPIキー認証なのかが未定。これはログインフロー・認可ミドルウェア全体の設計に影響する。

**関連箇所**: 520〜521行（未決定事項）

### C-3. パスワードリセット後の既存トークン失効戦略が不完全

A-05（パスワードリセット実行）では `RevokeAllByUserId` を呼んでいるが、A-04（リセット**要求**時）では既存の RefreshToken を失効していない。リセット要求から完了までの間、攻撃者が保持する旧トークンが有効なままになる。

**関連箇所**: 458〜470行（パスワードリセットフロー）

## 🟠 Major（実装前に解決が必要）

### M-1. ドメインイベントの定義漏れ（3件）

| 不足しているイベント | 根拠 |
|---|---|
| `TenantDeleted` | T-04ユースケースあり、`tenant.deleted` 監査ログあり、ドメインイベント定義なし |
| `UserUnlocked` | U-07ユースケースあり、ドメインイベント定義なし |
| メール検証イベント | A-06ユースケースあり、ドメインイベント・監査ログ定義なし |

**関連箇所**: 84〜86行（Tenantドメインイベント）、119〜123行（Userドメインイベント）

### M-2. 監査ログの記録タイミングに抜け漏れ（4件）

「記録タイミング」セクション（367〜404行）に以下が未記載：

| 抜け | 対応ユースケース |
|---|---|
| `auth.token.refresh` | A-02 `RefreshTokenUseCase` |
| `auth.lockout` の記録タイミング | U-03（自動ロック時に誰が呼ぶ？） |
| `user.unlocked` | U-07 `UnlockUserUseCase` |
| A-06（メール検証）対応のログ | `VerifyEmailUseCase` |

**関連箇所**: 347〜349行（記録対象イベント）、367〜404行（記録タイミング）

### M-3. `auth.lockout` の記録責務が宙に浮いている

ドメインイベント不要（Identityが自動管理）としながら、監査ログ定義には `auth.lockout` が存在する。**誰がいつ `IAuditLogRepository.AppendAsync(auth.lockout)` を呼ぶのか**が設計上明確ではない。Identity の `SignInResult.IsLockedOut` を `LoginUseCase` で検知してログ記録するフローを明記すべき。

```
// 明記すべき記録フロー（案）
LoginUseCase
  ├─ SignInResult.IsLockedOut → IAuditLogRepository.AppendAsync(auth.lockout)
  └─ SignInResult.Succeeded  → IAuditLogRepository.AppendAsync(auth.login.success)
```

**関連箇所**: 123行（UserLockedイベント不要の注記）、347行（auth.lockoutの監査ログ定義）

### M-4. RefreshToken ローテーション戦略が実装モデルに反映されていない

未決定事項に「RefreshTokenローテーション（7日推奨）」とあるが、`RefreshToken` 集約に `IssuedFromTokenId`（旧トークンへの参照）や「ローテーション時に旧トークンを自動失効する」ロジックが定義されていない。ローテーションを採用するなら集約設計への反映が必要。

**関連箇所**: 131〜139行（Session集約）、518行（未決定事項）

### M-5. U-03「アカウントロック」の実装責務が空白

ユースケース定義では「実行者：システム（自動）」とあるが、Application 層の UseCase クラスが存在しない。`LoginUseCase` 内で `SignInResult.IsLockedOut` を受けて監査ログを書くフローで吸収する設計なのか、明示が必要。

**関連箇所**: 168行（ユースケース定義）、244〜264行（Application層構成）

## 🟡 Minor（実装中または後続設計で対応可能）

### m-1. IP アドレス取得の実装詳細が不足

レート制限の定義はあるが、プロキシ・ロードバランサ経由での `X-Forwarded-For` の扱いが未定義。IP スプーフィング対策も未言及。

**関連箇所**: 446〜450行（レート制限）

### m-2. `user.invited` の記録タイミングが曖昧

招待メール送信時点か、ユーザーアクティベーション完了時点か、どちらで `user.invited` を記録するかが不明確。

**関連箇所**: 388行（記録タイミング）

### m-3. `AuditLog.Detail`（JSONカラム）の仕様が未定義

各イベントタイプで何を格納するか未記載。例：`user.role.changed` なら変更前後のロール両方を含めるべき。監査ログの価値は Detail の充実度に依存するため、最低限の項目定義が必要。

**関連箇所**: 361行（Detailカラム定義）

### m-4. ログイン成功時の既存 RefreshToken 管理が未記載

新しい RefreshToken を発行するが、同一ユーザーの過去のトークンを残すか失効させるかの方針がない。デバイス数が増え続けるリスクがある（O-04の「制限なし」方針と合わせて要検討）。

**関連箇所**: 290〜323行（ログインフロー）、493行（O-04）

### m-5. 監査ログの `fire-and-forget` のリスクが軽視されている

P-02 で「fire-and-forget またはバックグラウンドキュー」と記載されているが、fire-and-forget はプロセスクラッシュ時に監査ログが欠損する。コンプライアンス要件次第では**バックグラウンドキューを推奨**と明示すべき。

**関連箇所**: 502行（P-02）

### m-6. テナント削除時のカスケード挙動が未定義

`Status=Deleted` にした場合、テナント内のユーザー・RefreshToken をどう扱うか未記載（ログイン禁止にするか？既存セッションを即時失効させるか？）。

**関連箇所**: 493行（O-03）

### m-7. ロール変更の昇格ルールが未定義

U-06「ロール変更」の実行者は `TenantAdmin` だが、自分自身を `SystemAdmin` に昇格できるかなどの制約ルールが未定義。

**関連箇所**: 171行（ユースケース定義）

## ✅ 設計として評価できる点

- **情報漏洩対策のログインフロー設計**（テナント整合性チェックをパスワード検証後に置く）は適切

- **推奨インデックスが網羅的**に定義されている
